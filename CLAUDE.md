# MineMate

## Current structure

- `entity` — the `LivingEntity` body and PlayerEngine controller. Never call `controller.setOwner`; MineMate owns planning/auth. Also `CompanionDirectory`: the server-level authority on who owns which companion and where it last was — SavedData (`minemate_companions` in overworld storage) for identity/last-known location plus a runtime loaded-entity cache maintained by entity load/unload events. `loadedCompanionOf` scans the cache against live `getOwnerUuid` (ownership is reassignable, counts are tiny); an unloaded companion is never force-loaded — callers get the last-known entry for a deterministic line instead of a model call.
- `task` — goals, probes, supervision, and structured outcomes; the stable layer the planner drives.
- `task.sink` — chat, logging, journal, TTS, planner, and test consumers of task lifecycle events.
- `tool` — the typed, schema'd capability surface over `Goals`: descriptors, parameters, JSON `ToolCall`s, pure validation, and world binding. The single source of truth for what the companion can be asked to do; both `command` and `planner` go through it, so a tool cannot behave one way when typed and another way when planned.
- `context` — world snapshots, the recent-event journal, replan triggers, and `ConversationLog`: the bounded conversational memory (typed OWNER_UTTERANCE/COMPANION_UTTERANCE/ACTIVITY entries, whole-turn-group eviction so a wire transcript can never start with an orphan assistant head, serialized into entity NBT under `minemate_conversation` so conversation survives save/load while active plans deliberately do not). Bounds come from `chatTranscriptTurns`/`chatTranscriptChars` in `config/minemate.json` via `MineMate.plannerConfig()`. Depends on `task`/`entity`, never on `planner`.
- `chat` — `CompanionSpeech`, the single gateway for everything presented as companion speech: an owner-private `<Name>: ...` line, recorded verbatim as a COMPANION_UTTERANCE (display and memory cannot disagree), 100-tick exact-text dedup, and a static observer hook that is the headless suite's only observable for outbound chat (FakePlayer swallows `sendSystemMessage`). Task lifecycle telemetry keeps the `[MineMate]` prefix and never enters the log. `CompanionChatListener` routes ordinary owner chat (observe-only on `CHAT_MESSAGE`, so public chat displays untouched): eligible when within `chatEarshotBlocks` (unless `chatRequiresName`) or when prefixed by the complete companion name plus a word boundary — matched with `regionMatches`, never regex, and stripped before the model turn. Exact name-addressed forms `stop`/`stop that`/`cancel`/`cancel that` take `CompanionStop.stop` (the one deterministic stop sequence, shared verbatim with `/companion stop`) with zero model calls. An addressed-but-unloaded companion gets a last-known-location line via plain `sendSystemMessage` — the entity is absent, so nothing may enter its conversation memory.
- `planner` — the response seam and execution. `Planner.plan` returns `CompletableFuture<CompanionResponse>` (speech, actions+contract, or an `OrderClose`) — speech with nothing executable is conversation, and `Plan` is action-only: it exists only after dispatch validated a response's actions, so there is no empty or terminal plan anywhere. `ConversationCoordinator` (one per companion, server-thread-only) owns request concurrency: one hosted request in flight, a single generation counter whose `RequestTicket` (generation, origin, order epoch and plan id at begin) decides staleness and applicability at apply time, owner turns queued/coalesced behind an in-flight request (newer text stales the in-flight result; a stale completion still frees the slot so the queue can flush), a debounced chat path with a rolling per-minute cap (`chatDebounceMs`/`chatRequestsPerMinute`; `submitOwnerTurnNow` — commands and harness — never debounces or throttles), one deferred-replan slot replayed only while the same order is open, and `invalidateAll()` as the single stop-time invalidation (explicit at stop/plan-cancel/removal — `PlanExecutor.cancel` no longer discards requests). Dispatch runs two chains: the *owner chain* (OWNER_CHAT plus its continuation/repair, recognized by a null trigger) opens a `StandingOrder` only at acceptance via `PlanExecutor.startOwnerAction` — the atomic replacement: cancel old plan (evidence harvests into the old ledger before the swap), publish superseded, close old order, open fresh order with a fresh monotonic epoch, seed contract+baselines, commit; its bounded repair is request-local on the coordinator, a contract-only reply becomes a request-local `PendingCommitment` (no order, no ledger, speech buffered until covering actions are accepted), failures preserve unrelated work ("I am still working on: ..."), a speech-only reply preserves any open order (a mid-plan status question keeps plan/goal/epoch/ledger identity), and an accepted close never leaves a plan running. The *autonomous chain* keeps order-scoped budgets, the stored contract as authority, remainder coverage on PLAN_FINISHED replans, and closes the order on failure. `PlanExecutor.prepare` owns contract coverage via `CoverageScope` (NONE/FULL/REMAINDER) so `commit` only ever receives a fully disciplined plan, and waits one handoff tick after a replacement so the superseded goal can leave the supervisor before the first submit. `PlannerRequests.owner` is the one owner-utterance builder: it snapshots the transcript *before* recording the new text so the utterance appears exactly once on the wire. `PlannerConfig` reads `config/minemate.json`, generated on first launch; `PlannerAutonomy` is the only thing that turns a replan trigger into a request, charges every one against a `StandingOrder` budget, and defers (never drops) a trigger that fires while owner conversation is pending.
- `planner.llm` — the wire layer, in two stacked seams. `LlmBackend` is one provider's request/response mapping — `OpenAiResponsesBackend` and `AnthropicMessagesBackend` today, selected by the `provider` field of `config/minemate.json` inside `HostedPlanner.of`, defaulting to `anthropic`/`claude-sonnet-5`; `HttpTransport` sits under it so the headless suite can drive the real request builder and response parser with canned bytes. Nothing above `LlmBackend` knows which provider is installed, and the reply-shape rules live once in `PlannerProtocol.assemble` — a backend only turns bytes into speech plus named calls, so the two providers cannot drift semantically. `LlmPrompt` carries the conversation as `List<LlmTurn>` (asserted: non-empty, starts and ends with USER, no consecutive same-role); `PlannerPrompt.turns` renders it — historical owner text as `PLAYER:` lines, companion lines with the `<Name>: ` prefix stripped so the model is not taught to speak its own name, ACTIVITY entries folded into the *next* user turn under an `ACTIVITY RECORD` header, and the newest user turn = snapshot, REPLAN/LEDGER/REPAIR lines, trailing activity, then `PLAYER: <text>` for OWNER_CHAT or `ORDER (open): <text>` for other origins. Old turns never carry snapshots, so staleness is structurally impossible.
- `command` — `/companion` commands, all resolved through `CompanionDirectory` (any distance, any dimension; the 128-block proximity query is gone). `/companion plan` is a deterministic alias into the owner chat path (`submitOwnerTurnNow`) and opens nothing itself; spawn exclusivity uses `hasCompanion`, refusing even for an unloaded or cross-dimension companion; dismiss requires a loaded one; the no-companion failure names whether none exists or where an unloaded one last was.
- `integration` — isolated PlayerEngine configuration and compatibility quirks.
- `dev` — sequential headless integration test. On PowerShell, use `.\gradlew.bat "-Dminemate.autotest=true" runServer --console=plain` for the default smoke profile, or add `"-Dminemate.autotest.profile=full"` for all scenarios. Put quoted system properties before the task name. The task provisions `run/` and regenerates the world each time, preventing save-state contamination between clean sequential runs. It halts the server cleanly whether or not scenarios pass, so CI asserts on the `AUTOTEST PASS` log line rather than the Gradle exit code.
  Pass `"-Dminemate.autotest.scenario=<name>"` as well to run one or more comma-separated scenarios while debugging; explicit scenario selection overrides the profile.
  Every scenario is offline except `llm_live` and `llm_live_multi_step`, which are in no profile and run only when named. Each spends one real API call to check the planner integration against the provider — model id, endpoint, strict schema, reply parsing — and deliberately asserts nothing about PlayerEngine execution, since that would make a live check hostage to skill bugs. They need a key in `run/config/minemate.json` or the environment.

Build with `gradlew build`; launch a client with `gradlew runClient`. The project is pinned to Minecraft 1.21.1, Java 21, and Mojang mappings.

## Development lessons

- Keep verification proportional to the change. Small, low-risk changes such as command
  arguments or simple entity metadata should use build and manual verification rather than
  expanding the headless integration suite.
- A timed-out terminal/tool invocation does not necessarily stop the Gradle wrapper or the Minecraft JVM it launched. Before rerunning a timed-out headless test, inspect Java command lines and stop only the exact stale wrapper and `KnotServer` processes. Never kill every Java process; Gradle daemons, the IDE, and other tools may also be using Java. Stale-test symptoms include `Unable to delete run/logs/latest.log`, `Unable to delete run/logs/debug.log`, inconsistent scenario results, and port conflicts. A regenerated world cannot isolate two servers that are running concurrently.
- Prefer a focused scenario while changing one capability and the smoke profile for normal local verification. CI runs the complete `full` profile, including slow world-acquisition coverage. `runServer` can report `BUILD SUCCESSFUL` after an autotest failure because the test shuts the server down normally; the authoritative result is `[autotest] AUTOTEST PASS` or `AUTOTEST FAIL` in the log.
- PlayerEngine's craft macro used 300- and 1,200-tick collection cutoffs around a nested gather search that can run for 90 seconds. Compatibility patches must preserve the overall MineMate timeout, be guarded by the exact PlayerEngine dependency version, and use Mixin `require = 1` so upstream bytecode changes fail fast.
- `LivingEntityInventory.insertStack` mutates the supplied stack. Item pickup accounting must compare the stack count before and after insertion, report only that delta, discard a fully consumed entity without restoring its stack, and leave the mutated remainder for a partial pickup.
- `GiveItemToPlayerTask` considers delivery finished after throwing the items, not after the owner receives them. Fetch must treat acquisition and delivery as separate phases and remain active until the owner's inventory confirms the requested increase. Once delivery begins, do not re-enter acquisition merely because thrown items are no longer in the companion inventory.
- `fetch_items` is the multi-item delivery objective: one `ITEM_LIST` tool call, expanded by `OwnerGiveItemsTask` into a fresh `OwnerGiveItemTask` per entry, best effort — an entry whose acquisition exhausts is skipped, the rest still deliver, and the goal ends `BLOCKED/resource_unavailable` with a probe-authored detail naming delivered and missing items (`TaskTerminalResult.detail` overrides the supervisor's standard prose). Its `have`/`want` count whole entries, never item units, and `FetchItemsProbe` keeps advance monotone across item transitions by latching a per-entry score; the active entry's `PipelineProgress` restarts per item and must never be shared between entries. Duplicate entries merge everywhere they enter (registry coercion and `Goals.fetchItems`), because two consecutive `isEqual` children make PlayerEngine reuse the previous stopped child instead of restarting it.
- The `ITEM_LIST` schema is authored pre-strict in `ToolRegistry.propertyOf`, like the contract tool: the OpenAI strict transform rewrites only the top level and its null stripping is shallow, so the nested entry carries its own `required` (every nested field) and `additionalProperties: false`, and Anthropic takes the same shape verbatim. `ContractCoverage` counts both `fetch` and `fetch_items` toward deliverable coverage from the raw wire JSON.
- An "unavailable" resource is only cleanly unavailable to `ResilientAcquisitionTask` when nothing in the inventory feeds its craft macro. In the best-effort autotest, holding oak planks alongside an impossible bucket let the bucket attempt craft a table, register inventory progress, and fund retries past the scenario cap; the held second entry must be inert to the first entry's pipeline (dirt), not an ingredient of it.
- A loaded Fabric `FakePlayer` is not necessarily in the connected-player list. Owner resolution should first check connected players and then loaded `ServerPlayer` entities. In delivery tests, vanilla `FakePlayer.playerTouch` may remove an item entity while its old stack object remains readable; phantom-drop assertions should cover entities collected by `CompanionEntity`, while delivery success is verified from the fake owner's inventory.
- A headless autotest destination must stay inside the spawn entity-ticking region. With no real players, a companion that pathfinds beyond it freezes mid-walk with `tickCount` stopped, and because the supervisor ticks from the entity, no stall or timeout can fire either — the scenario dies only by hard cap, while Baritone still reports `isPathing=true` and the probe shows a frozen distance. Chunk offsets proven ticking by `goto_success`/`goto_y` are around (+24, +8) from spawn; a diagonal (+20, -20) already freezes.
- A headless mob fixture must set its vanilla retaliation state directly. `EntityHelper.isAngryAtPlayer` requires `mob.getTarget() == companion`, and letting the kill aura bootstrap that state makes the scenario depend on PlayerEngine state that is created once per companion and reset by nothing.
- Replacing a chest or furnace fixture with air invokes vanilla container removal and drops its contents. Empty test containers before removing their blocks, or the companion can collect the drops in the next scenario and create misleading results such as `withdraw 6/4`; changing fixture coordinates or adding task-drain delays does not prevent those world item drops.
- Keep player-visible status, progress, failure, truncation, and autotest-marker punctuation ASCII. The log files may be valid UTF-8 while a console or copy path still decodes em dashes and ellipses incorrectly; comments may retain Unicode.
- `/companion stop` must cancel the plan before the supervisor. Cancelling only the supervisor lets `PlanExecutor` submit the next step on the following tick, so stop appears to do nothing.
- `PlanExecutor` polls `supervisor.lastOutcome()` for its own goal id rather than registering a `TaskListener`. `TaskListeners` has no unregister, so a per-companion listener leaks for every dismissed companion; and reacting inside `fireFinished` would start the next step from within the previous step's terminal callback, on a supervisor still mid-finish. Polling also makes a mid-plan chat order correct for free: the supervisor cancels the step as `superseded` and the ordinary outcome branch ends the plan.
- The plan executor uses `submit`, never `replace`, so a plan cannot silently steamroll an order the owner just gave; `BUSY` is the signal to abandon.
- Journal pickup and damage events must coalesce. A `mine 64 cobblestone` goal produces a pickup every few ticks, and without merging them the 64-entry ring holds nothing but pickups by the time a planner reads it.
- `ReflexSnapshot.startedAtTick` is measured against `CompanionReflexTelemetry`'s own per-entity-load counter, not game time. Use `CompanionEntity.reflexActiveTicks()` to turn it into a duration.
- `ReflexSnapshot.defenseSuppressed` is inverted relative to its name: true means mob defense is suppressed. Render it as a word (`mob_defense=leashed|active`), never a raw boolean, or the planner reads it backwards.
- World snapshots are captured on demand and memoized per game tick. Do not prime them from `CompanionEntity.tick()`; that spends raycasts and entity queries per companion per tick for a consumer that may never ask.
- Never use `Long.MIN_VALUE` as a "never happened" sentinel for a tick timestamp that gets subtracted. `observedTicks - Long.MIN_VALUE` overflows to a negative difference, so a cooldown guard reads as permanently unexpired; `ReplanTriggers` silently fired nothing at all. Use an explicit sentinel and branch on it before subtracting.
- Assert a floor, not only a ceiling, on anything whose job is to be rare. `context_journal` capped replan triggers at 4 per scenario, which a system firing zero triggers satisfies perfectly. The suite passed while the feature was dead.
- Numeric tool arguments must be checked for finiteness before range. Both `value < min` and `value > max` are false for NaN, so `"NaN"` — which `Double.parseDouble` accepts — validates against every bound and reaches pathfinding as a value no later check recognises.
- OpenAI's Responses API declares tools **flat** — `{type, name, description, parameters}`. The nested `{type, function: {...}}` form belongs to Chat Completions and is rejected here for a missing name. The reply's `output` is a heterogeneous array whose order is not guaranteed and which normally leads with a `reasoning` item, so filter it by `type` and never index `output[0]`. `function_call.arguments` arrives as a JSON *string* that needs a second parse.
- OpenAI strict mode has no way to mark a tool parameter optional. Every optional one must be listed in `required` and typed as a null union, so the model correctly sends `"count": null` — which `ToolRegistry` rejects, while treating an *absent* key as the parameter's default. The backend must strip null-valued arguments before building a `ToolCall`; without it every plan touching a defaulted parameter is rejected as `invalid_argument`. `minimum`/`maximum`/`minItems` are honoured under strict mode, so keep them.
- Anthropic's Messages API takes the registry's neutral `{name, description, input_schema}` tools **verbatim** — no flat transform, no null unions, and no null stripping on the way back, because `tool_use.input` arrives as a parsed object rather than a string. Do not request Anthropic strict mode: its schema engine rejects `minimum`/`maximum`, and `ToolRegistry` re-validates every argument anyway. `tool_choice` is the object `{"type": "auto"}` — forcing tool use with `"any"` suppresses the assistant text block (OpenAI's `tool_choice` is likewise `"auto"`, since a zero-call speech reply is legal conversation now). Even under `"auto"`, live `claude-sonnet-5` with adaptive thinking reliably answers an action order with tool calls and no text block, so the protocol accepts a speechless action reply — blank dialogue reaches the owner as nothing, and the goal-start chat line covers them — while the prompt merely requests speech. Never make speech a hard reply requirement on action replies; it broke every live action order. The prompt cache needs an explicit `cache_control` breakpoint on the system block, `content` is a typed block array that normally leads with `thinking` blocks, a truncated reply announces itself only through `stop_reason: "max_tokens"`, and 529 `overloaded_error` is retryable. Headers are `x-api-key` plus a mandatory `anthropic-version`, never `Authorization: Bearer`.
- `report_order_status` is a hosted-protocol function, not a world capability. Append it after reading `ToolRegistry.schemaJson()`; never register it in `ToolRegistry` or expose it through `/companion tools`. Its statuses are `COMPLETED/CANCELLED/UNSUPPORTED/BLOCKED` — `ANSWERED` and `CLARIFICATION` are retired because answering and asking are conversation, not order lifecycle; the retired names are rejected as malformed statuses. Assistant speech beside the status call is legal: the displayed (and remembered) line is the speech when nonblank, else the status `message` fallback — exactly one COMPANION_UTTERANCE either way. A reply with speech and nothing else is conversation; a fully empty reply (no speech, no calls, no status) stays malformed so silence fails loudly.
- Resolve an API key most-specific-first — system property, then the provider-scoped file field (`anthropicApiKey`/`openaiApiKey`, so both providers' keys can sit in `config/minemate.json` at once), then the plain `apiKey` field, then the provider-keyed `MINEMATE_ANTHROPIC_API_KEY`/`MINEMATE_OPENAI_API_KEY`, then `ANTHROPIC_API_KEY`/`OPENAI_API_KEY` — and log which source won. Ambient variables are set once and forgotten; letting one beat the file someone just edited produces a 401 naming a key they do not recognise. Never log the key itself, and keep it out of `describe()`. Blank `baseUrl`/`model` follow the provider's defaults, so switching provider is a one-field edit.
- `PlannerConfig.of` takes its provider explicitly rather than stamping the default, so a change of `DEFAULT_PROVIDER` can never silently repoint the autotest fixtures or the live scenarios at a different wire format. An unknown provider makes the config unusable instead of guessing an endpoint shape.
- `MineMate.installPlanner()` refuses to install a hosted planner during an autotest run, whatever the environment holds. The suite must not be able to reach the network or bill an account; its planner scenarios install their own hosted planner over a `FixtureTransport` instead.
- `HostedPlanner` applies its own `orTimeout` rather than trusting the transport's. A request that never completes leaves `isPlannerRequestPending()` true forever, which silently disables replanning for that companion for the rest of the session.
- Half of what a planner must get right produces no outcome to assert on: a failure, a timeout, malformed speech with no status or tool calls, or a request cancelled mid-flight must all leave the companion idle. `Scenario.probe(name, ready, verdict, ...)` covers that shape — `ready` says when to look, `verdict` returns null for pass. Goal-identity checks in the harness skip probe scenarios, because a probe may drive whole plans of its own.
- Scenarios that assert on the presence *or absence* of a journal event must clear the journal in setup. The 64-entry ring outlives a scenario, so `llm_timeout` legitimately leaving a `PLANNER_FAILED` behind would otherwise decide whether `llm_talk_only` passes.
- PlayerEngine assigns a task's `controller` when it first *ticks* it, and `ResourceTask.isFinished()` dereferences that controller. Never ask a freshly created child task whether it is finished — `OwnerGiveItemTask` did, and crashed the server on the first tick of any `fetch` whose resource is not craftable. It went unnoticed because `oak_boat` resolves to a craft macro, whose `isFinished` touches no controller.
- A loaded Fabric `FakePlayer` does not run vanilla's player collision/pickup loop, so thrown items never reach it on their own. Delivery scenarios must simulate `playerTouch` for drops that actually touch the owner. Without it a fetch looks like it stalled during acquisition when in fact it had already acquired and thrown.
- A `FakePlayer` that has completed a delivery, been discarded, and re-added from Fabric's profile cache stops receiving deliveries: the next scenario's fetch sits at 0/N until its cap. Any scenario that completes a real delivery must own its fake-owner profile (UUID and name) outright, never reuse `FAKE_OWNER_UUID`.
- A reach-blocked container task must recover with `GetCloseToBlockTask` (a ratcheting `GoalNear` that forces a walk around the obstruction), never `GetToBlockTask`, whose `GoalBlock` demands standing inside the container's own block and is unsatisfiable — the pathfinder wanders and the stall budget kills the goal. For the same reason, never pin `BoundedContainerTransferTask` in its NAVIGATE phase (e.g. by gating its arrival `closerThan` on reach): that phase's only recovery is its own memoized `GetToBlockTask`. Gate the container access itself (resolve/validate/transfer) instead.
- The order ledger (`OrderLedger` on `StandingOrder`, seeded by `declareContract`) holds measured
  evidence only: delivered units are owner-inventory deltas, latched by the fetch probes
  (`DeliveryEvidenceSource`) and harvested by `PlanExecutor` when a step ends on any path -
  the probe outlives the goal because the `Goal` record holds it, so cancelled steps still
  yield their receipts. A `COMPLETED` claim on a deliver-to-owner contract is validated against
  the ledger (after `refreshFromOwner`, which credits items picked up in the throw-to-pickup lag
  window) and an unevidenced claim goes through the one bounded repair; `PLAN_FINISHED` replans
  are validated against the undelivered remainder via `ContractCoverage.remainderViolation`,
  while `DAMAGE_TAKEN` replans stay exempt so threat responses are not forced into fetches. The
  ledger reaches the model as a `LEDGER:` line in the user prompt, never the cached SYSTEM block.
- Planner results are asynchronous, so every completion carries a `RequestTicket` claimed on the server thread by `ConversationCoordinator.begin()`. Without it a plan requested before `/companion stop` still arrives and starts seconds later, and two concurrent requests race. `stop` calls `invalidateAll()` unconditionally, not inside the `isActive()` branch: a request can be in flight while the supervisor is busy with a manual order. A stale completion must still free the in-flight slot (`completeInFlight` matches the ticket, not the current generation), or the queued owner turn behind it can never dispatch.
- A cancelled supervisor goal takes a tick to leave the supervisor, and `submit` is refused while it winds down. An atomic replacement (`startOwnerAction`) must therefore set the handoff flag and let `PlanExecutor.tick` wait for supervisor idle before submitting the replacement's first step — without it the new plan dies `CANCELLED/superseded` one tick after it started. The flag is set only when the replacement itself cancelled a goal, so a plan submitted over a *manual* goal still dies superseded as intended.
- Mid-plan scenarios that assert a plan is still running must give both the original and any replacement plan a *far* goto target: a `goto` whose target is already within acceptance range succeeds in zero seconds and the verdict sees an idle executor. Chunk (+24, +8) from spawn is the proven ticking region for long walks.
- Per-companion state that outlives a scenario needs explicit isolation, exactly like the journal ring and conversation log: the chat rate limiter's rolling window spans scenarios (consecutive scenarios compress the rolling minute into seconds), so chat scenarios call `resetChatCap()` in setup/teardown; directory entries persist in SavedData for the whole run, so chat teardown calls `clearEntries()`.
- A harness FakePlayer sits in the level's entity list, not the server `PlayerList`, so `ServerMessageEvents` never fires for it. Chat routing scenarios must call `CompanionChatListener.handle` directly with the FakePlayer as sender; the real event wiring is only verifiable in a live client.
- A fetch accepted with no owner resolvable blocks `owner_offline` on its first step; with a zero replan budget the resulting `PLAN_FINISHED` trigger closes the order through budget exhaustion before a verdict can look. Scenarios that assert on an open order after accepting a fetch need a fake owner (with its own profile UUID) so the plan genuinely runs.
- The unevidenced-`COMPLETED` denial needs a real order with a real ledger, which since acceptance-time orders means an accepted fetch that failed to deliver (the no-owner block above is the cheap way); a contract-only reply followed by `COMPLETED` never opens an order, so the close correctly degrades to conversation and validates nothing.

## Known issues

`craft_iron_sword_world` is order-sensitive: it passes alone (~89s) but can exhaust its cap after a
different preceding sequence. `fetch_items_best_effort` is likewise marginal against its cap: it
passes alone (~134s) but has exceeded the cap both after long preceding sequences and, once,
nearly alone — world-generation and timing variance, not scenario order alone.

## Where this is going

- **World context:** event-triggered, budgeted snapshots (~300 tokens) covering state, threats, current work, recent events, and player-relative position.
- **Memory:** episodic history, semantic facts/preferences, and spatial landmarks; evaluate PlayerEngine's `elliegps` waypoint system first.
- **Task depth:** encode real game knowledge—Y-levels, routes, safe bridges, spawn-proofing, and torch spacing—as deterministic tasks.
- **Learned skills:** persist and retrieve named goal compositions that worked; structured outcomes are their training signal.
- **Reflection:** turn failures into lessons and recall them before similar attempts.
- **Initiative and personality:** emerge from the 20 Hz loop and event triggers, not only a system prompt.
- **Player modeling:** infer what the player is doing and needs so the companion can help usefully without being prompted.
